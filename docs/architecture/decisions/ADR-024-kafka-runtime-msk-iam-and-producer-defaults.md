# ADR-024: Kafka Runtime: Amazon MSK with IAM Auth and Producer Defaults

## Status

Proposed

## Date

2026-10-08

## Context

ADR-019 fixes topic names, keys and the event envelope but not where Kafka runs or how services authenticate to it. ADR-009 places the estate on AWS; the platform pillar has published the Kafka runtime the platform repositories provide (platform contract, 2026-10-08, owned by the platform pillar). Services need one way to connect in AWS and one way to run locally, and producers need durability defaults that are not left to each squad.

## Decision

1. **AWS: Amazon MSK.** In AWS environments (dev, staging, prod; default region `me-central-1`) Kafka is Amazon MSK, Kafka 3.6 or later, TLS in transit.
2. **IAM client authentication.** Services authenticate with IAM: `security.protocol=SASL_SSL`, `sasl.mechanism=AWS_MSK_IAM`, using the service's own IRSA role (ADR-023). No shared Kafka users, no SCRAM passwords for services.
3. **Topic-scoped IAM policy.** Each service's role gets an IAM policy generated by the Terraform module `msk-client-access` in `fintechbankx-platform-delivery-iac-terraform-modules`, scoped to the topics it produces to (its own `evt.<ctx>.<aggregate>.*` topics) and the topics and consumer groups (`cg.<service-id>.*`) it consumes. Producers to another context's topics are not granted.
4. **Strimzi only for local and non-AWS.** The `kafka` namespace with Strimzi is for local development and non-AWS clusters. Service configuration switches between the two by environment, not by code.
5. **Producer defaults.** `acks=all`, `enable.idempotence=true`. Topics are created with replication factor 3 and `min.insync.replicas=2`. Local single-broker setups may lower RF and ISR; shared environments may not. Weakening these to clear an alert is not allowed (see `docs/runbooks/OPEN_FINANCE_OBSERVABILITY_RUNBOOK.md`, Kafka Replication).
6. **DLQ.** Dead-letter topics follow ADR-019: `evt.<ctx>.<aggregate>.dlq.v<major>`, with the same RF and ISR, and IAM write access only for the consuming service that dead-letters to it.

## Alternatives

- **Self-managed Kafka (Strimzi) on EKS in AWS.** Rejected for AWS: operational load of brokers, storage and upgrades without benefit over MSK.
- **SASL/SCRAM or mTLS client auth on MSK.** Rejected: separate credential lifecycle; IAM reuses IRSA and gives topic-level policy.
- **Fold into ADR-019.** Not chosen: naming is cluster-agnostic and should not change if the runtime does.

## Consequences

- Every service's IRSA role and `msk-client-access` policy must exist before it can produce or consume; topic access changes are Terraform changes reviewed by the Event Platform Squad.
- Services need the AWS MSK IAM auth library on the classpath for AWS profiles.
- Durability defaults raise per-message latency slightly in exchange for no acknowledged-message loss on a single broker failure.
- Moving off MSK later is reversible at the configuration level but costly (re-provisioning, re-authorisation).
- Related: ADR-009, ADR-017, ADR-019, ADR-021, ADR-023.
